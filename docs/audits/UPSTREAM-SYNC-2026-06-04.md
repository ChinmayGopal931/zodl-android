## 1. Executive summary

The headline item is the **REQUIRED Zcash network-compatibility update** upstream shipped across 3.5.1/3.5.2 ("This update is required to ensure continued wallet functionality"). The consensus logic lives inside the Zcash SDK Rust backend, so the app-side work is just **bumping the SDK 2.4.8 → 2.6.1-SNAPSHOT** (carried upstream in three steps) plus a default-server reorder; because the fork consumes the SDK via `includeBuild` at a pinned SHA (not Maven), this MUST be hand-reconciled and coordinated with the SDK repo — it cannot be cherry-picked. The bump renames `rescanFromHeight → rewindToHeight` and adds abstract `Synchronizer` members that the fork's `MockSynchronizer.kt` (androidTest) must satisfy or the build breaks. Alongside the SDK work, there are **four self-contained security/correctness fixes the fork is genuinely missing**: the swap-proposal exact-zatoshi fix (`#2198`, silent truncation/overflow of swap send amounts), the ExchangeRate-falls-back-on-any-CMC-error fix (MOB-1195), the zec.rocks default-server reorder (MOB-1322), and the testnet-Internal-flavor `bools.xml` network-routing fix (`#2209`). A larger group of upstream money/privacy fixes (MOB-987 locale formatting, MOB-1103 correct-account shielded addresses, MOB-982 Tor refactor, clipboard hardening) are **already independently present** in the fork and need no action. **Total portable count: 11 items** (4 P0, 5 P1, 2 P2); the rest are SKIP (UI/branding, CI/release-infra, test-automation, integration merges, voting feature, and upstream's reverted multi-server broadcast).

### P0-3 — Exact zatoshi conversion for swap proposals (`#2198`)

**Why:** `RequestSwapQuoteUseCase.createProposal()` L144 (verified) still builds `ZecSend(amount = Zatoshi(quote.amountIn.toLong()), ...)`. `toLong()` SILENTLY truncates fractional zatoshi and overflow-wraps an oversized `BigDecimal` to a wrong (possibly negative-magnitude) `Long` → an incorrect ZEC amount spent. This feeds both the Zashi and Keystone proposal builders, and the fork's P2P.me offramp + NEAR swap reuse this path.

**Steps:**
- [ ] Read `ui-lib/src/main/java/co/electriccoin/zcash/ui/common/usecase/RequestSwapQuoteUseCase.kt` (confirm `Zatoshi` and `java.math.BigDecimal` imports).
- [ ] Add at end of file:
  ```kotlin
  internal fun BigDecimal.toExactQuoteZatoshi(): Zatoshi =
      try { Zatoshi(longValueExact()) }
      catch (e: ArithmeticException) { throw InvalidSwapQuoteAmountException(this, e) }

  internal class InvalidSwapQuoteAmountException(val amount: BigDecimal, cause: ArithmeticException) :
      IllegalArgumentException("Swap quote amount must be an exact zatoshi value: $amount", cause)
  ```
- [ ] Change L144 `amount = Zatoshi(quote.amountIn.toLong()),` → `amount = quote.amountIn.toExactQuoteZatoshi(),`.
- [ ] Ensure the new throw is inside `createProposal()`'s existing try/catch (which calls `navigateToErrorUseCase(ErrorArgs.General(e))` / `keystoneProposalRepository.clear()`); widen the catch if needed so a malformed quote shows the fork's swap error UI rather than crashing.
- [ ] (Recommended) Add `ui-lib/src/androidTest/.../usecase/RequestSwapQuoteUseCaseTest.kt` with the 4 upstream cases: accepts whole number, accepts whole-number-with-scale (`123.0`), rejects non-integral (`123.9`), rejects overflow (`9223372036854775808`).

**Risks:** new THROW on fractional/overflow `amountIn` where the old code silently produced a wrong send — desired safer behavior but must surface via the fork's error UI, not an uncaught crash. Validate against a real **P2P.me** quote that `amountIn` is denominated in zatoshi (it is for NEAR; confirm for P2P.me) so `toExactQuoteZatoshi()` doesn't over-reject.

**Verification:** `./gradlew :app:installZcashtestnetFossDebug`; run the new test; drive a real swap/offramp quote and confirm the resulting zatoshi matches `quote.amountIn`, and an artificially fractional `amountIn` surfaces a swap error (no crash).

## 6. Risks & coordination

- **SDK includeBuild pin (`.zapp-deps`).** The fork consumes the SDK from `../zcash-android-wallet-sdk` via `includeBuild`, guarded by `file(...).exists()` in `settings.gradle.kts`. The `.zapp-deps` SHA (`88499ad`) is documentation-only (CI's `verify_sha` covers zappMessaging + bare-kit, NOT the SDK; CI builds the SDK from Maven). Bumping requires the real SHA for `2.6.1-SNAPSHOT` from the SDK team. **Do NOT blank `SDK_INCLUDED_BUILD_PATH`** like upstream — the exists()-guard keeps source builds working.
- **CLAUDE.md SDK rule.** "Don't bump the SDK SHA without coordinating with upstream-sync work." P0-1's first step is that coordination. The bump and its consuming-code fix MUST ship together (the androidTest won't compile otherwise).
- **SNAPSHOT in production.** `2.6.1-SNAPSHOT` is a moving artifact; `gradle.properties`/CLAUDE.md both warn to use a non-snapshot before a production release. For release, pin via the source SHA or a tagged 2.6.x.
- **ZappMessaging interaction.** None with the Synchronizer interface (chat is Bare/holepunch JNI, not Ktor/Tor HTTP, no rescan/rewind/treeState refs). But per CLAUDE.md, if JS changes were pulled in `../zappMessaging/`, run `npm run build:android` there before `./gradlew` — a stale bundle can fail the same build command and be misattributed to the SDK bump.
- **Offramp interaction.** Real for Ktor (P1-4 — smoke-test a live order; documented allowance/fee atomic-cancel sensitivity), for the swap exact-zatoshi fix (P0-3 — confirm P2P.me `amountIn` is zatoshi-denominated before shipping), and for the Tor-timeout note (P1-3 — offramp NEAR/CMC route over Tor). No offramp interaction with the Synchronizer rewind/treeState API.
- **Build-verification gating.** Every batch must pass `./gradlew :app:installZcashtestnetFossDebug` before merge. The SDK batch additionally needs Maven-fallback resolution, androidTest compile, and a **mainnet** debug runtime sync smoke (testnet shows "Offline — reconnecting" because `lightwalletd.testnet.cipherscan.app` is currently down — expected, not a regression, and it masks SDK-bump success on testnet).
- **Release-config hygiene (CLAUDE.md).** Before tagging, diff `gradle.properties` vs the last release tag: confirm only intended version/dep lines changed and no `*_LOG_LEVEL=debug` / `*_NETWORK=<flavor>` overrides slipped in.
- **Fork-of-a-fork debt.** INV-3's in-repo `CurrencyFormatterExt` and the manual SDK/version edits must be reconciled on the next upstream sync (delete the in-repo copy once the SDK exposes the formatters; re-point imports).
- **Out-of-scope CVE flag.** `BOUNCY_CASTLE_VERSION=1.78.1` (fork-only, offramp/evm crypto) is old and never existed upstream — handle in a separate dependency-security pass, not this sync.
