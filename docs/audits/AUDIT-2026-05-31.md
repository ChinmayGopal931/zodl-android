Two multi-agent workflows ran fork-vs-upstream, each finding → **adversarial verification** (a second, skeptical agent re-opened the code to confirm or refute every high/security finding; false positives were dropped and several severities corrected down or up):

## 3. Prioritised remediation checklist

Severities are the verifier-corrected values. Items are grouped so a cluster can be fixed in one pass. IDs link to the full finding in §4/§5.

### P0 — fix before any release (HIGH, in-repo, exploitable or data-exposing)

- [ ] **Screenshot-protect the chat seed reveal.** `seed-dialog-missing-securescreen` / `seed-reveal-dialog-no-securescreen` (cross-confirmed). `ChatProfileSeedPhraseDialog.kt` shows the 24-word mnemonic with no `SecureScreen()` — it is the *only* seed surface in the app missing it (wallet-backup, restore, PIN screens all call it). Add `SecureScreen()` as the first statement, matching `WalletBackupView.kt` / `RestoreSeedScreen.kt`.
- [ ] **Require re-auth on the BIO→PIN switch.** `switch-bio-to-pin-no-reauth` / `disable-auth-no-reauth-bio-to-pin` (cross-confirmed). `SecuritySettingsViewModel.kt:130-132` jumps straight to new-PIN setup with no credential check → anyone holding a briefly-unlocked phone can replace the app lock. Gate the transition on `biometricRepository.requestBiometrics()` (mirror `triggerBioEnrollment` at `:197-217`) and don't write `APP_PIN_HASH`/`AUTH_METHOD` until it succeeds.
- [ ] **Bound image decoding.** `image-decode-dos-no-bounds`. `ImageProcessor.kt` / `MediaBubble.kt` / `ImageViewerOverlay.kt` call `BitmapFactory.decode*` on attacker-controlled images with no size/dimension limits → OOM / decompression-bomb DoS. Add `inJustDecodeBounds` pre-check + `inSampleSize` downsampling and a max-pixel cap.
- [ ] **Harden the seed→SDK boundary.** `seed-plaintext-string-across-sdk-boundary` / `chat-seed-joined-string-not-zeroed` (cross-confirmed, partly ⚠ out-of-repo). The wallet mnemonic crosses into the JS worklet as an immutable, never-zeroed `String`. In-repo: drop the bespoke `joinedString()` (use the SDK's `joinToString()`), minimise the lifetime of the joined string. Out-of-repo: confirm the worklet does not log it (`ZAPP_MESSAGING_LOG_LEVEL=debug` dumps keypairs) and stores entropy encrypted (see `chat-identity-entropy-plaintext-at-rest`).
- [ ] **Decide on chat-identity ↔ wallet-seed coupling.** `chat-identity-seed-coupling-no-domain-separation`. The chat identity derives from the funds seed with no domain separation, linking the (publicly-shared) chat pubkey to the wallet. Add domain separation in derivation, or accept and document the linkage as a product decision.
- [ ] **Biometric is a spoofable boolean gate.** `biometric-no-cryptoobject-binding`. No `CryptoObject` binds auth to a Keystore key (upstream-inherited, TODO #7), so on a compromised device success can be forged. For the highest-value reveals (seed/private-data export) bind to a Keystore key with `setUserAuthenticationRequired(true)` + `setInvalidatedByBiometricEnrollment(true)`; at minimum document the threat model.

#### `image-decode-dos-no-bounds` — Unbounded BitmapFactory decode of attacker-controlled images/thumbnails (OOM / decompression-bomb DoS)

**🔴 HIGH** · _security_ · main sweep

- **Where:** `ui-lib/src/main/java/co/electriccoin/zcash/ui/screen/chat/media/ImageProcessor.kt` : 19-22, 38-41; MediaBubble.kt 92-93; ImageViewerOverlay.kt 73-74
- **Root cause:** Every decode path calls BitmapFactory.decodeStream / decodeByteArray with no inJustDecodeBounds pre-pass, no inSampleSize, and no pixel-dimension or byte cap. compressImage/generateThumbnail decode the FULL bitmap into memory before scaling, so a 100MP picked image allocates hundreds of MB and can OOM-crash the app. More critically, MediaBubble.kt and ImageViewerOverlay.kt decode message.thumbnailData — base64 supplied by the REMOTE peer over the wire (MimeTypes.kt documents these as on-wire fields) — via Base64.decode + decodeByteArray with no size guard. A hostile peer can send a thumbnail whose declared/decoded dimensions are enormous and crash every recipient's chat (remote DoS).
- **Evidence:** `ImageProcessor: `BitmapFactory.decodeStream(it)` (no Options). MediaBubble: `val bytes = Base64.decode(message.thumbnailData, Base64.DEFAULT); BitmapFactory.decodeByteArray(bytes, 0, bytes.size)` on peer-supplied data.`
- **Upstream contrast:** No upstream chat-image rendering; fork-introduced untrusted-content decode without the standard inSampleSize guard.
- **Fix:** Do a bounds-only decode first (inJustDecodeBounds=true), reject when width*height exceeds a cap, compute inSampleSize, then decode downsampled. Cap thumbnailData base64 length before Base64.decode; prefer handing remote thumbnail bytes to Coil with an explicit size constraint over raw decodeByteArray.

#### `switch-bio-to-pin-no-reauth` — BIO->PIN switch performs NO authentication before letting the user set a brand-new PIN and flip the active unlock method

**🔴 HIGH** · _security_ · main sweep

- **Where:** `ui-lib/src/main/java/co/electriccoin/zcash/ui/screen/securitysettings/SecuritySettingsViewModel.kt` : 130-132, 172-194
- **Root cause:** In onSaveChanges(), the branch `menu.selectedTab == "pin" && menu.currentMethod == "biometric"` routes straight to SecuritySettingsState.SettingNewPin(SwitchFromBiometric) with NO authentication step (the doc comment at line 120 explicitly says 'BIO -> PIN: skip bio-verify, go straight to new PIN setup'). onNewPinConfirmed() then writes a new APP_PIN_HASH and sets AUTH_METHOD="pin". # Zapp Fork Audit — 2026-05-31

## 1. Executive summary

**Overall health: Cautiously shippable, with one credential-takeover bug to fix first.** The fork is, on balance, competently engineered. The two fork-added crypto modules (`offramp-lib`, `evm-lib`) are unusually clean — BIP-44 key derivation from the wallet seed through a zeroized `CharArray`, redacted `toString()`/`hashCode` on `EvmKey`, low-s ECDSA, constant-time MAC compare, fail-closed bundler-key handling, and HTTP logging that redacts API-key query params. Release-config hygiene in `gradle.properties` is genuinely strong: every secret/flavor-selecting property ships safe-by-default, cleartext is forbidden by `network_security_config`, and the manifest's new exported surface is limited to the existing launcher alias plus a non-exported `FileProvider`. The biometric/PIN auth gate is correctly built (PBKDF2-HMAC-SHA256 @ 100k iters, per-credential salt, constant-time compare, cleared `PBEKeySpec`, authoritative lockout checked before the hash) and the fork did **not** weaken any upstream biometric check, including upstream's important fix removing biometric "graceful degradation."

The weaknesses cluster in two places: **(a)** the chat UI/financial layer over-trusts peer-controlled message fields, and **(b)** the wallet seed and the derived chat identity are handled more loosely on the chat path than on the offramp path. There is also one real **auth bypass** in the fork-authored security-settings screen, and a large volume of mechanical style drift confined almost entirely to that same `securitysettings` feature.

**Top 5 to fix first (prioritized):**

1. **[P0] BIO→PIN switch performs no re-auth** (`SecuritySettingsViewModel.kt:130-132`, corrected **high**). Anyone with momentary access to an already-unlocked, biometric-protected app can set their own PIN and take over the app lock. The three sibling transitions all re-verify; this one does not. One-branch fix.
2. **[P0] Chat seed-phrase dialog has no `SecureScreen()`/`FLAG_SECURE`** (`ChatProfileSeedPhraseDialog.kt:20-83`, **high**). The full 24-word wallet mnemonic is screenshottable and shows in the recents thumbnail — the single worst surface to leave unprotected, and the only seed-bearing surface in the app that omits the protection every sibling uses. One-line fix.
3. **[P0] Chat identity entropy persisted as plaintext JSON** (`zappMessaging/core/lib/identity.js:136-146`, corrected **medium**, high impact). Seed-equivalent BIP-39 entropy is written unencrypted to `identity.json` despite the SDK README claiming Keystore protection, and the "delete identity" path never deletes the file.
4. **[P1] Financial bubbles + chat-driven send are spoofable/unverified** (`ChatMessageBubble.kt`, `TransactionBubble.kt`, `ChatRoomVM.kt:598-603/832-837`). Peer-declared `contentType` chooses which financial card renders; "Send ZEC" pre-fills the recipient from the latest peer wallet-address bubble with no validation or key binding. Display-only today — lock the trust model down before any "Pay"/"Accept" affordance is added.
5. **[P1] Untrusted-media decode is unbounded** (`ImageProcessor.kt`, `MediaBubble.kt`, `ImageViewerOverlay.kt`, **high**). No `inJustDecodeBounds` pre-pass or dimension cap; a hostile peer's oversized thumbnail can OOM-crash every recipient (remote DoS). Pair with EXIF-strip-on-all-paths and filename sanitization before shipping media to untrusted peers.

## 2. Security findings

### 2.1 Seed / chat-identity derivation & key storage (LEAD)

**`chat-identity-entropy-plaintext-at-rest` — corrected MEDIUM (high impact)**
`zappMessaging/core/lib/identity.js:136-146` (save), `:35` (storagePath), `:99-129` (load)
`Identity.save()` writes `{ publicKey, entropy(hex), displayName, createdAt }` to `identity.json` under the bare worklet's `--data-dir = context.filesDir` (`BareWorkletManager.kt`) with **no** Keystore / `EncryptedFile` / `EncryptedSharedPreferences`. The 32-byte hex entropy round-trips back to the Ed25519 keypair, so it is seed-equivalent for the messaging identity. **Risk:** on a rooted/forensic/same-UID-exposure path another process recovers the entropy and clones the user's identity / decrypts stored conversations. The fork's own `PersistableWallet` (EncryptedPreferenceProvider) and `AddressBookKey`/`MetadataKey` (Keystore-cacheable) are the in-repo standard this bypasses. **Fix:** wrap `identity.json` with a Keystore-derived key (pass a per-install key from Kotlin, or use `EncryptedFile`).
*(Corrected: the earlier claim that the file also stores `seedPhrase`/`secretKey` verbatim was withdrawn — it stores only the four fields above.)*

**`readme-storage-claim-mismatch` — MEDIUM**
`zappMessaging/android/README.md:17`
README advertises "Secure seed storage via Android Keystore (EncryptedSharedPreferences)"; a repo-wide grep finds that string only in the README — no Kotlin/JS code uses Keystore/EncryptedSharedPreferences, and the security-crypto dependency isn't even on the classpath. **Risk:** reviewers/integrators assume at-rest protection that does not exist, masking the finding above. **Fix:** implement the claimed storage or correct the README to state "plaintext app-private file."

**`chat-seed-joined-string-not-zeroed` — corrected MEDIUM**
`ChatBootstrap.kt:130-148, 171-172`
`derive()` materializes the mnemonic as an immutable `String` (`request.wallet.seedPhrase.joinedString()`), passes it to `sdk.restoreFromSeedPhrase`, which puts it in a `JsonObject` and marshals over bare-kit IPC. JVM strings can't be zeroed; the joined seed and the JSON copy linger on the heap until GC. The seed-bearing `PersistableWallet` is additionally pinned as the last value of the `distinctUntilChanged` combine and in the cached `AutoDeriveRequest`. **Contrast:** the fork's own `WalletSeedPhraseSource` returns a zero-fillable `CharArray` and `StaticOfframpAccountProvider`/`EvmKeyDerivation` wipe it in `finally`. **Fix:** have the SDK accept a `CharArray`/`byte[]` wiped in `finally`; avoid pinning `PersistableWallet` in a flow-cached object.
*(See also `wallet-seed-crosses-jni-as-plaintext-string`, corrected **low** — same egress, traced through `IPCBridge` NDJSON to the worklet; severity bounded because the upstream SDK `SeedPhrase` already stores the seed as an immutable `String`, so this only widens an existing window.)*

**`exportseedphrase-roundtrip-string-no-flag-secure` — MEDIUM**
`ChatProfileVM.kt:379-386, 166-172`
The revealed mnemonic is held in `pendingSeedPhrase: MutableStateFlow<String?>` (survives config changes, re-split per recomposition), cleared only by `null` on dismiss (GC-dependent), and the dialog has no `FLAG_SECURE`. The reveal **is** correctly gated behind biometric/`PinAuthGate` (a genuine strength). **Fix:** hold the seed in a `CharArray` wiped on dismiss and set `FLAG_SECURE` while shown. (The `FLAG_SECURE` gap is also tracked as the P0 `seed-dialog-missing-securescreen`.)

**`seed-dialog-missing-securescreen` — HIGH (confirmed, kept)**
`ChatProfileSeedPhraseDialog.kt:20-83`
The full 24-word mnemonic (`SeedWordGrid`) renders in a Material3 `AlertDialog` with no `SecureScreen()`. Every other seed/PIN surface — `WalletBackupView`, `RestoreSeedScreen`, `PinVerifyScreen`, `PinSetupScreen`, `SecuritySettingsView` — calls it; this fork-authored dialog is the lone omission, so the mnemonic is screenshottable and appears in the recents thumbnail. `FLAG_SECURE` is orthogonal to the auth gate (it defends against screenshot/recents/screen-capture, which the gate does not), so the gate does not downgrade this. **Fix:** call `SecureScreen()` inside the dialog. One line.

**`deleteidentity-shutdown-swallowed-no-file-wipe` — corrected MEDIUM**
`DeleteChatIdentityUseCase.kt:28-50`
`runChatCall("…shutdown failed") { sdk.shutdown() }` swallows any exception (logs `Twig.warn`, continues), and `sdk.shutdown()` only tears down the IPC/worklet session — it does **not** delete `identity.json` or the worklet data dir. The use case clears prefs/address-book/metadata and calls `walletCoordinator.deleteSdkDataFlow()` (Zcash SDK store only), then the caller force-kills the process. **Risk:** a user who "deletes" their chat identity leaves a recoverable, seed-equivalent entropy file on disk — cosmetic deletion of the most sensitive artifact. **Fix:** after shutdown, explicitly delete the worklet data dir (`filesDir/bare`, `…/zappmessaging`, `…/corestore`, `identity.json`) and assert absence before declaring success.

**`zapp-messaging-log-level-release-guard-missing` — corrected LOW**
`gradle.properties:113`
Committed default `ZAPP_MESSAGING_LOG_LEVEL=` is blank/safe; per CLAUDE.md `debug` "ships keypair dumps … into release BuildConfig." There is no build-time assertion that fails a release when the resolved level is `debug`, so a stray override could ship verbose messaging logging. **Fix:** add a release-variant assertion that throws on `debug` (in the `:zappmessaging` consumer module where the BuildConfigField is emitted); audit worklet debug logs; exclude `diag.log` from backups.
*(Corrected: the earlier "worklet logs the Ed25519 secret key at debug" claim was withdrawn — no such line was found.)*

### 2.2 Native / JS bridge trust boundary

**`ipc-bridge-lenient-unauthenticated-events` — MEDIUM**
`IPCBridge.kt:21-24, 96-179, 254-283`
`IPCBridge.json` is `isLenient = true` + `ignoreUnknownKeys = true`, and `handleEvent()` dispatches any object with a `type` and no `id` to all handlers with no origin/auth/schema check. `ZappMessagingSDK.setupEventHandlers` then mutates app state directly from these events: `connection.status → _isOnline`, `message.received → UI`, `media.download_complete → a filePath the UI later File()/decodes`, and `senderId` (which drives both the block filter and the financial bubbles). `parseMessage` applies no length bound on `content` (only display *names* are capped); a line is bounded only by the 1 MB receive buffer. **Risk:** the worklet is a semi-trusted relay of fully-untrusted peer data; a malicious peer or JS-core bug can spoof messages, forge `senderId`, or supply attacker-chosen media paths. **Fix:** validate event payloads against a strict schema before dispatch; bound content size; normalize `senderId`; confirm media paths resolve under the app media dir.

**`ipcbridge-trusts-worklet-events-unauthenticated` — corrected LOW**
`ZappMessagingSDK.kt:710-844`
The inbound `setupEventHandlers` re-emits every worklet event (`message.received`, `member_added`, `message.status`, `peer_status`, plus payment/wallet-address types) to the UI as authoritative with only null-presence checks — no signature, no participant check, no replay/dedup at this layer. **Corrected low:** this is defense-in-depth; authentication/replay protection legitimately belongs in the encrypted-transport/JS core, which was out of scope. The cited outbound `sendPaymentMessage` routing is *not* a trust-boundary issue (conflated by the original draft). **Fix:** document/verify the JS core authenticates+dedups every event; add boundary checks for high-impact events (reject `member_added`/payment/wallet-address whose `senderId` isn't a known participant; dedup by id).

> **Scope caveat (read findings §2.2 together):** the JS worklet core and the blind-peer/DHT transport — where message authentication and replay protection would actually be enforced — live in the JS bundle, outside the Kotlin file scope and not auditable here. Combined with the unpinned composite builds (§3 / §6), **this boundary cannot currently be audited or pinned.**

### 2.3 Auth / biometric / PIN gate

**`switch-bio-to-pin-no-reauth` — corrected HIGH (was critical)** — P0
`SecuritySettingsViewModel.kt:130-132, 172-194`
`onSaveChanges()` branch `selectedTab == "pin" && currentMethod == "biometric"` routes straight to `SettingNewPin(SwitchFromBiometric)` with **no** authentication (doc comment: "BIO → PIN: skip bio-verify"). `onNewPinConfirmed()` then writes a new `APP_PIN_HASH` and sets `AUTH_METHOD="pin"`. `ChangePinScreen` (`SecuritySettingsView.kt:376-550`) only collects two 6-digit entries — no biometric prompt anywhere on this path. The other three transitions correctly require `submitCurrentPin`/`requestBiometrics` first, so this is an internal-inconsistency, exploitable bypass: momentary access to an unlocked app → set own PIN → flip the active method → app-lock takeover/owner lockout. Downgraded from critical only because it's bounded to local physical access to an already-unlocked app and doesn't itself expose seed/keys/funds. **Fix:** require `biometricRepository.requestBiometrics(...)` to succeed before entering `SettingNewPin` when `currentMethod == "biometric"`.

**`bio-enroll-blanks-pin-and-resets-lockout` — corrected MEDIUM**
`SecuritySettingsViewModel.kt:205-209`
After a successful biometric prompt, `triggerBioEnrollment()` writes `APP_PIN_HASH=""`, `FAILED_PIN_ATTEMPTS_COUNT=0`, `PIN_LOCKOUT_END_WALLTIME_MS=0`. **(1)** This contradicts the screen's own copy ("A PIN fallback is always kept as backup," `SecuritySettingsView.kt:301`) and destroys the fallback if biometrics are later invalidated. *(Mitigation verified: `verifyAndUpgradePin` returns false on an empty stored hash, so the scary empty-PIN-as-valid bypass does **not** exist — which is why this is medium, not high.)* **(2)** A successful biometric (no PIN knowledge) clears an in-progress PIN brute-force lockout. **Fix:** keep a separate `pinSet` flag instead of blanking the hash; reset attempt/lockout counters only inside the verified-PIN success branch.

**`pin-lockout-in-unencrypted-prefs` — MEDIUM**
`PinAuthGate.kt:64-87`
`FAILED_PIN_ATTEMPTS_COUNT` and `PIN_LOCKOUT_END_WALLTIME_MS` are stored via the **unencrypted** `StandardPreferenceProvider` (not the `EncryptedPreferenceProvider` that holds the PIN hash), and the lockout check is wall-clock (`if (lockoutEnd > now)` with `System.currentTimeMillis()`). **Risk:** a rooted user / ADB backup on a debuggable build can zero the counters between guesses, and advancing the device clock past the deadline clears the cooldown with no file edit — fully defeating the online rate limit (offline brute force still bounded by PBKDF2 100k × 10⁶ keyspace). The same VM already uses `SystemClock.elapsedRealtime` with backward-clock detection for the session timeout. **Fix:** move both keys to `EncryptedPreferenceProvider`; anchor the deadline to `elapsedRealtime()` with reboot/backward-clock handling; consider escalating lockout duration.

**`pin-plaintext-in-string-not-zeroed` / `pin-handled-as-immutable-string` — corrected LOW / corrected MEDIUM**
`PinVerifyScreen.kt:55,49,67-69`; `SecuritySettingsView.kt:385-386,397,482-483`
The PIN is held in `rememberSaveable { mutableStateOf("") }` (serialized into the saved-instance Bundle on process death) and passed as immutable `String` through `submitPin` → `tryVerify` → `hashPinV2`, so it can't be zeroed. The downstream `pbkdf2()` correctly clears its `PBEKeySpec`. **Fix:** use plain `remember` (not `rememberSaveable`) for the digit buffer; carry the PIN as `CharArray` and zero it in `finally` after hashing.

**`pin-gate-crypto-correct` — informational (clean baseline)**
`EncryptedPreferenceKeys.kt:42-105`
PBKDF2-HMAC-SHA256, 100k iters, 256-bit, 16-byte SecureRandom salt (`v2$salt$hash`); constant-time `MessageDigest.isEqual`; `PBEKeySpec` cleared in `finally`; legacy SHA-256 upgraded in place; lockout checked **before** comparison; upstream `BiometricPrompt` config preserved (BIOMETRIC_STRONG/DEVICE_CREDENTIAL by API level) and the upstream fix removing `ERROR_NO_BIOMETRICS`/`ERROR_NO_DEVICE_CREDENTIAL` auto-unlock is intact; `PinVerifyScreen` calls `SecureScreen()`. **No bypass.** The only forward step is TODO[#7] (bind verification to a Keystore key with `setUserAuthenticationRequired`).

**`settings-pin-biometric-gate-missing-on-delete-and-no-seed-row` — corrected LOW**
`ChatSettingsVM.kt:177-195`
`ChatSettings`'s "Delete" button (which calls only `sdk.shutdown()` — a benign session teardown, **not** the destructive wipe) is ungated, while the read-only seed reveal in `ChatProfile` is gated. A real UX/threat-model inconsistency, but the original "destroys identity in two taps" framing was wrong (a verifier flagged injected/fabricated tool output steering toward a non-existent `clearIdentityData()`; the SDK has only the benign `shutdown()`). **Fix:** route any genuinely destructive delete through the same biometric/`PinAuthGate` flow.

### 2.4 Financial actions from chat bubbles

**`financial-bubbles-spoofable-no-verification` / `content-type-spoof-financial-bubble-routing` — corrected MEDIUM**
`ChatMessageBubble.kt:60,137-152,174-182`; `TransactionBubble.kt:30-69`; `PaymentRequestBubble.kt:30-66`
`resolveContentType()` trusts the peer-set `message.contentType` (or, for `text/plain`, an embedded `contentType` JSON field) to route into `PaymentRequestBubble` / `WalletAddressBubble` / `TransactionBubble`. `TransactionBubble` renders "ZEC received" + `"$amount ZEC"` + `tx: <sig>` from `JSONObject(message.content)` with **no txid lookup against the wallet's own transactions, no signature verification, no settlement check**. Any peer can make a message render as an authentic-looking "ZEC received 5.0" card. **Verified mitigation:** all three financial bubbles are dispatched with only `message + isFromMe` and **no** send/navigation callback — display-only today, so no one-tap fund loss. **Risk:** spoofable financial-confirmation UI is a phishing primitive and the exact seam a future "Pay this request" button would sit on. **Fix:** derive transaction bubbles from the local wallet's confirmed inbound txs by txid; frame payment-request/address cards as "unverified, sent by `<peer>`"; add an invariant comment that these bubbles must never gain a one-tap financial action.

**`send-recipient-from-chat-bubble` / `chat-peer-wallet-address-unverified-payment` — corrected LOW / MEDIUM**
`ChatRoomVM.kt:598-603, 832-837`
`onSendZecClick()` → `resolvePeerWalletAddress()` returns `messages.value.lastOrNull { contentType == WALLET_ADDRESS && !isFromMe }?.content` (only an `isNotBlank()` check, **last-wins**, no Zcash-address validation, no participant-key binding) and forwards it into `UnifiedSendArgs(recipientAddress = …)`. **Verified mitigation (drives the low/medium split):** the downstream `UnifiedSendViewModel` runs `validateAddress(args.recipientAddress)` (`:242-248`), disables the Review button unless the address validates (`:783-791`), renders the address in an **editable, user-visible** field, and there is no auto-send — the standard Zashi proposal/confirmation flow runs before any funds move. So a malformed blob is rejected; the residual risk is a **valid-but-attacker-owned** address pre-filled with no provenance shown. **Fix:** bind the pre-fill to a verified contact's stored `walletAddress`, validate before use, and surface the source/peer on the send-confirm screen.

**`walletaddr-untrusted-address-verbatim-copy` / `wallet-address-bubble-untrusted-clipboard-qr` — corrected MEDIUM**
`WalletAddressBubble.kt:48-131`
`address = JSONObject(message.content).optString("content", message.content)` (catch-all fallback to raw content) is QR-encoded, displayed verbatim, and long-press-copied via `CopyToClipboardUseCase` with no Zcash-address validation and no "unverified source" caption. **Risk:** clean address-substitution vector feeding a later manual send; the look-alike attack (valid-but-attacker-owned address) is the real residual. Note format validation alone does **not** stop the look-alike — the missing **provenance caption** is the meaningful mitigation. **Fix:** SDK-parse the address before QR/copy; render unparseable strings as inert text and suppress the QR; show "address provided by `<peer>` — verify before sending."

**`location-bubble-untrusted-geo-intent` — corrected MEDIUM**
`LocationBubble.kt:44-87`
`lat`/`lng` come from `JSONObject(message.content).optDouble(...)` with no range check, and on tap the bubble does `Uri.parse("geo:$lat,$lng?q=$lat,$lng")` via string interpolation → `startActivity(ACTION_VIEW)` with no `runCatching` guard. **Risk:** a crafted `application/location` message controls the implicit-Intent URI and free-text `?q=` segment; realistic harm is a crash when no geo handler exists (no guard) plus `?q=` label abuse — not code-exec. **Fix:** validate `lat ∈ [-90,90]`/`lng ∈ [-180,180]`; if invalid render inert text; build the URI with `String.format(Locale.US, "geo:%f,%f", …)`; sanitize/drop `?q=`; wrap `startActivity` in `runCatching`.

**`bubble-untrusted-amount-token-verbatim` — corrected LOW**
`PaymentRequestBubble.kt:31-66` (+ `TransactionBubble.kt`)
`amount`/`token`/`memo` rendered verbatim with no allowlist/length/numeric bound. `Text()` renders plain strings (no markup/intent sink), bubbles are display-only — equivalent capability to any peer typing arbitrary text, so low. **Fix (hardening):** clamp/format `amount`, allowlist `token`, cap memo/token length, frame unverified tx claims as peer assertions.

### 2.5 Other security findings

**`exif-gps-leak-gif-file-path` — corrected MEDIUM**
`FileUtils.kt:10-21` (`copyUriToCache`); routed at `ChatRoomVM.kt` (GIF ~743, file ~752/763)
`compressImage` re-encodes static images through a Bitmap (drops EXIF — safe), but the GIF branch and the **file-picker** branch use `copyUriToCache`, a raw byte copy that preserves EXIF. So the *same* camera-roll JPEG is scrubbed via the gallery picker but ships GPS/device fingerprint to the peer and the blind-peer relay if sent as a GIF or via the file picker — an inconsistent privacy guarantee. **Fix:** strip EXIF on **every** outgoing image path (`ExifInterface` clear `GPS_*`/`DATETIME`/`MAKE`/`MODEL`, or always re-encode); document that arbitrary files are forwarded with metadata intact.

**`filename-path-traversal-copyuritocache` — corrected MEDIUM**
`FileUtils.kt:13-14, 23-40`
`getFileName()` returns the content provider's `DISPLAY_NAME` (or `uri.lastPathSegment`) verbatim → `File(dir, fileName)` with no sanitization. A malicious/buggy provider returning `../` escapes `chat_media` (within the app sandbox — clobbers sibling cache files). The same unsanitized name is later the `FileBubble` label. **Fix:** `File(name).name` to drop directories, reject `..`/separators, bound length, and verify `destFile.canonicalPath.startsWith(dir.canonicalPath)` before writing.

**`image-decode-dos-no-bounds` — HIGH (kept)** — P1
`ImageProcessor.kt:19-22, 38-41`; `MediaBubble.kt:92-93`; `ImageViewerOverlay.kt:73-74`
Every decode path (`decodeStream`, and `decodeByteArray` on peer-supplied base64 `thumbnailData`) runs with no `inJustDecodeBounds` pre-pass, no `inSampleSize`, and no dimension/byte cap. `OutOfMemoryError` is an `Error`, not caught by the `catch(Exception)` guards. ## 5. Correctness / maintainability bugs

**`newconv-only-first-participant` — MEDIUM** (`NewConversationVM.kt:162-183`): the UI supports multi-select (FlowRow of participant chips, add/remove/toggle), but `onStartChatClick` takes `selectedParticipants.value.firstOrNull()` and creates a DIRECT chat with `listOf(firstPublicKey)` — selecting ≥2 contacts **silently drops** all but the first. **Fix:** restrict selection to one, or branch to a GROUP conversation when `size > 1`.

**`moderation-impl-non-atomic-sync-prefs` — MEDIUM** (`ChatModerationRepositoryImpl.kt:34`): `blockUser`/`unblockUser`/`submitReport` are non-suspend, called from main-thread VM handlers; each does two **non-atomic** writes (`_blockedUsers.value = …` then `_blockedKeys.value = …`) to two flows meant to stay in lockstep, and persists via synchronous `getString`/`putString().apply()` on the main thread (incl. blocking reads in `init{}` during Koin construction). **Fix:** derive `blockedKeys` from a single `_blockedUsers` source (`map`/`stateIn`), make mutators suspend, confine load/persist to `Dispatchers.IO` (or DataStore).

**`sdk-resume-globalscope-leak` — corrected MEDIUM** (`ZappMessagingSDK.kt:697-706`): `resume()` does `GlobalScope.launch { getConnectionStatus() }` — the only `GlobalScope` use in the bridge — tied to no lifecycle, uncancellable by `shutdown()`. A resume that overlaps shutdown leaks a coroutine holding the IPC channel (up to the IPC timeout). **Fix:** a private `CoroutineScope(SupervisorJob() + Dispatchers.Default)` cancelled in `shutdown()`.

**`chatbootstrap-mainscope-derive-on-main` — MEDIUM** (`ChatBootstrap.kt:30,64-76,101-148`): `private val scope = MainScope()` launches three indefinite collectors in `init` with no `cancel()`/teardown on an app-singleton, pinning the seed-bearing `PersistableWallet` (cached `AutoDeriveRequest`) on Main indefinitely; `derive()` runs the seed-marshal + JNI restore round-trip **on Main** (only the bare-kit IPC init actually needs Main affinity), risking jank/ANR. **Fix:** own the scope with explicit cancellation (logout/delete); don't retain `PersistableWallet` in a cached flow value; dispatch the restore work off Main.

**`worklet-bundle-extraction-on-main-thread` — MEDIUM** (`BareWorkletManager.kt:52-62`): `start()` (invoked from `initialize()` on Main for native affinity) also does synchronous `mkdirs()` + `assets.open("worklet.bundle").copyTo(...)` + `getPackageInfo` + ConnectivityManager queries; on first launch and after every app update the whole 1.8 MB bundle is copied on the UI thread → ANR risk. **Fix:** hoist extraction + `getGatewayIp()` to `Dispatchers.IO`; keep only `Worklet()`/`IPC()` creation on Main.

**`lockout-countdown-duplicate-coroutines` — MEDIUM** (`SecuritySettingsViewModel.kt:84-88,96-105,163-165`): `launchLockoutCountdown()` launches an unbounded `while(true){…delay(1000)}` with no Job handle, from both `init` and the `Locked` branch — overlapping loops double-decrement the timer and leak a coroutine, making the anti-brute-force countdown unreliable. **Fix:** store the Job, cancel-and-restart on each call; single source.

**`chatlistvm-group-event-no-distinctness` — LOW** (`ChatListVM.kt:367`): invite-driven `delay(500); refreshConversations()` with no debounce → N full refreshes on an invite burst; member/group reducers `it?.map{}` silently no-op (event lost) when the cache is still null before the first load. **Fix:** move cache+reducers to the shared data layer with a non-null initial state; conflate refreshes.

## 7. Refuted / non-issues (checked and cleared — do not re-flag)

- **Outgoing media has no EXIF strip (broad claim) — REFUTED.** The camera and gallery-image paths route through `ImageProcessor.compressImage`, whose `BitmapFactory.decodeStream → Bitmap.compress(JPEG)` re-encode implicitly drops EXIF/GPS. The grep-for-`ExifInterface`-returns-nothing signal was misleading. The genuine residual (GIF + file-picker raw copy) is captured separately as `exif-gps-leak-gif-file-path` (med).
- **Chat moderation data backed up to cloud/adb — REFUTED.** Block-list/reports are plaintext `SharedPreferences` (a legitimate lower-severity hardening point), but the `auto_backup_config*.xml` is **include-only** (`address_book/` only), so under correct Android backup semantics everything else — including `chat_moderation.xml` — is **excluded**. The original finding inverted include-list logic.
- **R8 keep rules defeat obfuscation / `app/proguard-rules.pro` — REFUTED.** That file doesn't exist; the real `app/proguard-project.txt` sets `-dontobfuscate` globally (inherited upstream, open-source-wallet rationale), so the wildcard keeps only affect shrinking, not obfuscation.
- **`SendChatMediaMessageUseCase` is a `TODO()` stub — REFUTED.** It's a correct `runChatCallResult` wrapper returning `Result<ZMMessage>`; the earlier read was a tool glitch.
- **`scan-image-mutex-deadlock` — WITHDRAWN.** `onScanned()` launches a *new* coroutine for `mutex.withLock`, deferring acquisition until the outer block releases — the same working pattern as upstream `ScanGenericAddressVM`. No reentrancy.
- **`gradle.properties` BLIND_PEER block triplicated / each offramp key duplicated — WITHDRAWN.** Git confirms exactly one `BLIND_PEER` pair and one occurrence of each offramp key; both were misreads.
- **PIN uses a fast single-pass SHA-256 — RETRACTED.** It's PBKDF2-HMAC-SHA256 @ 100k iters (see `pin-gate-crypto-correct`).
- **`swap/lock/` is an auth gate / phantom `ChatDataSource.kt`, `SecureScreen.kt`, `SwapLock*.kt` paths — REFUTED.** `EphemeralLock*` is a privacy gap-limit confirmation sheet (3 files byte-identical to upstream, one a `Zodl→Zapp` brand edit), not auth; the named phantom files don't exist.
- **Manifest over-exposes new components — CLEARED.** The only exported surface is the existing launcher activity-alias (`zcash://`) and a non-exported `grantUriPermissions` `FileProvider`; `network_security_config` forbids cleartext on all domains (debug only widens trust anchors). `CAMERA`/`LOCATION`/`GPS` correctly pair `<uses-feature required="false">`.
- **Secret-logging sweep — CLEAN.** No seed/key/password interpolation in `Twig`/`Log`/`println` across `ui-lib`/`offramp-lib`/`evm-lib`/SDK; the one offramp HTTP log redacts API-key query params. The committed `gradle.properties` ships all secret/flavor props safe-by-default; `BLIND_PEER_KEYS` is a public relay pubkey; the git-ignored generated `BuildConfig.java` pubkey matches the public committed value (not a leak).

The findings above reflect post-verification, directly-read-from-source conclusions; the `settings-delete` finding in particular was corrected downward after the injection was disregarded.
